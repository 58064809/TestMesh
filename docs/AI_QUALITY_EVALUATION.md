# TestMesh AI 智能化测试质量评估基线

## 结论先行

TestMesh 当前已经证明“技术链路能运行、证据能追溯、人工能复核”，但尚未证明“在真实业务中能稳定发现足够多的问题和缺陷”。

因此不使用一个容易误导的“AI 综合质量分”。质量结论按三层给出：

1. **工程可用性**：结构、Trace、工具调用、Schema、运行成功率、时延和成本。
2. **任务有效性**：需求问题是否找对、测试用例是否覆盖风险、自动化是否能检出已知缺陷。
3. **真实泛化性**：换业务、换格式、换表达和换版本后是否仍稳定。

只有三层都达到门槛，才能称为“可用于真实项目准入”。

## 评估对象与主要指标

| 被测能力 | 主要指标 | 驱动指标 | 强制护栏 |
| --- | --- | --- | --- |
| AI 需求分析 | 已知问题召回率；人工确认率（精确率代理） | 重复问题率、问题类型覆盖、来源引用完整率 | 结构校验 100%；伪造引用 0；冲突至少 2 条引用 |
| 智能测试设计 | 风险/条件覆盖率；人工通过率 | 原子性、Gherkin 有效率、重复率、技法适配率 | Baseline 追溯 100%；未批准资产不得执行 |
| API/UI 自动化 | 已知故障检出率（Mutation/Fault Detection Yield） | 可执行率、稳定通过率、失败证据完整率 | `skip/fixme` 0；失败必须有请求/响应或 Trace |
| Agent 运行质量 | 同版本重复一致性；回归退化率 | 工具选择正确率、参数正确率、恢复成功率 | Trace 覆盖 100%；静默降级 0 |
| 运行效率 | P50/P95 时延；单次 Token/费用 | Docling、模型、工具各阶段耗时 | 超预算立即标记，不用质量分抵消成本超限 |

## 指标定义

### 需求问题识别

- `确认率 = (人工接受 + 人工合并) / 已完成评审的问题数`
- `重复率 = 人工合并 / 已完成评审的问题数`
- `召回率 = AI 命中的已知问题 / 人工金标准中的全部已知问题`
- `F1 = 2 × 确认率 × 召回率 / (确认率 + 召回率)`

当前 TestMesh 只能可靠计算确认率、重复率和引用完整率。因为评审流程尚未登记“人工发现但 AI 漏掉的问题”，所以召回率和 F1 必须显示为未知，不能拿“问题数量很多”代替。

### 测试设计

- `Baseline 覆盖率 = 被至少一个测试条件覆盖的有效 Baseline 条目 / 全部有效 Baseline 条目`
- `条件覆盖率 = 被测试用例覆盖的已批准 TestCondition / 全部已批准 TestCondition`
- `原子用例率 = 仅包含一个主要验证目标且结果可独立判断的用例 / 全部用例`
- `人工通过率 = 人工接受用例 / 已评审用例`

72 条 Approved v1 能证明当前 PRD 的测试资产已经人工确认，不能证明它们能发现真实程序缺陷。后者必须由故障注入或真实缺陷回流验证。

### 自动化执行

- `故障检出率 = 被测试集检出的已知故障 / 注入的全部有效故障`
- `可执行率 = 成功进入真实 Runner 的批准用例 / 计划执行的批准用例`
- `不稳定率 = 相同代码与环境重复运行时结果发生变化的用例 / 全部重复执行用例`
- `证据完整率 = 具备日志、请求/响应或 Playwright Trace 的失败 / 全部失败`

受控 API/UI 服务可以证明 Runner、配置和证据链路有效，但必须在页面和报告中标记为 `controlled`，不得冒充真实业务验收。

## 没有真实项目资料时的数据策略

继续使用现有 16 页中文 PRD 作为种子样本，并建立三类 Phoenix Dataset：

1. **人工标注集**：保存人工确认的问题、驳回项、合并项，以及人工补充的漏检问题。
2. **可追溯变异集**：只对种子 PRD 做单一、可定位的变化，例如删除主体、改变边界值、制造规则冲突、删除状态出口、加入不可验证词。每个变异预先记录期望检出点。
3. **执行故障集**：在受控 API/UI 目标中注入确定性故障，用 Schemathesis、Hurl、Playwright 和 Approved TestCase 验证是否真实报错。

这些数据属于“受控评估资料”，不是“生产数据”。它们适合建立第一条回归基线；以后获得真实需求、人工漏检、线上失败和缺陷单后，再按风险分层回流 Phoenix Dataset。

## 候选门槛（v0，待数据校准）

| 指标 | 候选门槛 |
| --- | --- |
| Schema / Gherkin / 引用校验 | 100% |
| 人工确认率 | ≥ 85% |
| 已知问题召回率 | ≥ 90% |
| 重复问题率 | ≤ 10% |
| 需求引用完整率 | 100% |
| 已知故障检出率 | ≥ 80%；高风险故障 100% |
| `skip/fixme` | 0 |
| 同版本重复运行 | 至少 3 次，并报告结果分布 |
| 起步评估集 | 至少 20 个高质量样本，覆盖主要格式和风险类型 |

这些是 TestMesh 的初始工程门槛，不是行业公认常数。积累真实数据后，应根据误报成本、漏检风险和运行预算重新校准，保留每次门槛版本及批准记录。

## 准入规则

发布判断采用“硬门槛 + 质量画像”，不把多个指标加权成一个总分：

- 任一护栏失败：`deny`。
- 召回率、故障检出率或样本覆盖仍未知：`review`。
- 所有强制门槛通过，且相对已批准版本无显著退化：`allow`。

Phoenix 继续负责 Dataset、Experiment、Trace、Evaluator、人工 Annotation 和版本比较；TestMesh 只显示业务质量目标、证据链接、人工决定和最终 `allow / deny / review` 语义，不新建另一套评测平台。

## 当前项目质量判断（2026-10-14）

- **工程可用性：已有证据。** Docling、Deep Agents、Phoenix、Schemathesis/Hurl、Playwright 的单一路径均已在真实 PRD或受控目标上跑通。
- **当前样本任务有效性：部分有证据。** 需求问题经过人工评审，72 条测试用例已人工批准；页面现在可计算确认率、重复率和引用完整率。
- **受控缺陷检出：已有初步证据。** 20 条单缺陷合成需求真实运行后检出 19 条，受控检出率 95%；但 1 条被证据 Gate 拒绝，12 条触发过度报告复核，因此准入仍为 `review`。
- **真实缺陷检出能力：证据不足。** API/UI 只有受控服务，没有真实业务契约、URL、账号和缺陷样本。
- **泛化与稳定性：未知。** 目前只有一个中文售后 PRD，未形成至少 20 个样本、3 次重复运行和系统化变异集。

所以当前正确结论是：**在受控样本上具备较好的缺陷发现能力，但存在运行完整性和过度报告风险；可作为演示和评估基线继续完善，不能声称已经具备企业真实项目的稳定质量保障能力。**
