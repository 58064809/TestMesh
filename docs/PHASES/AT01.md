# AT01 — Approved TestCase 到 API 自动化

## 状态

进行中。TD01 已于 2026-10-12 形成 Approved TestCase v1；AT01 已完成成熟能力复核、旧 P02 路径收敛和受控 Runner 验收。当前真实业务闭环等待项目 OpenAPI 3.x 契约与可测试环境，不使用虚构接口替代。

## 要解决的质量问题

- Approved TestCase 与实际 API 接口缺少可审计映射，自动化结果无法回链业务测试意图。
- 人工编写边界、随机和契约测试会重复成熟工具能力。
- 旧 P02 仍读取历史 SQLite 需求/证据，不能证明测试来自不可覆盖的 Approved TestCase 版本。

## 调研结论与单一路径

- **OpenAPI 3.x** 是 API 契约输入；TestMesh 不从 PRD 猜接口、参数或响应结构。
- API 执行按质量目标保留两个成熟引擎：**Schemathesis 4.29.3** 负责 OpenAPI 契约、examples、coverage、fuzzing 和 stateful 生成式测试；**Hurl 8.0.1** 负责确定性的多请求业务链、变量捕获与断言。两者不是备用或 fallback，页面显式选择执行目的。
- 业务场景执行器调研比较 Bruno CLI、Hurl、Newman 和 Karate。Bruno 功能完整但当前 CLI 依赖审计引入多项 high severity 漏洞；官方 Hurl npm wrapper也引入高危解压依赖，因此均未保留。最终使用 Apache-2.0 的 Hurl 官方 Windows 单文件二进制，版本和 SHA-256 固定，不引入 npm wrapper。
- TestMesh 不实现 HTTP Client、断言 DSL、请求编排、变量捕获、报告引擎或脚本沙箱，也不再为 AT01 引入代码生成 Agent/OpenHands。
- **项目配置采用两层边界**：TestMesh 只保存项目业务 ID、环境 Base URL、非敏感公共 Header 和外部配置引用；敏感配置的目标能力选用 Infisical。Infisical 已有 Project/Environment、版本、权限、审计、Node SDK 与私有部署能力，不在 TestMesh 重写。
- 当前电脑没有 Docker，不能完成 Infisical 私有部署的真实验收（官方 Compose 路径还需要 PostgreSQL 与 Redis）。因此当前可用路径只保存非敏感配置，Authorization、Cookie、Token、API Key 和密码由服务端拒绝落库，认证仅在单次运行内存中使用。不得以明文表或加密字段自研替代 Infisical。
- OpenBao 适合底层 KV/动态密钥但缺少贴合本产品的 Project/Environment 管理模型；Unleash 是 Feature Flag 平台；Backstage 是完整开发者门户，均不作为当前项目配置主路径。

## 已实施

- 旧 `/api/p02/*` 产品入口已移除；新唯一入口为 `/api/api-automation/*`。
- 新增独立“项目配置”入口，项目可维护多个测试环境。API 自动化必须选择项目和环境；OpenAPI 固化其项目/环境 ID，运行时由服务端读取 Base URL 与公共 Header，页面不能临时篡改目标。
- 导入 OpenAPI 前必须从下拉框选择不可覆盖的 Approved TestCase 版本；当前 v1 可读取 72 条批准用例。
- 每个 operation 可人工关联零到多条 Approved TestCase；只执行至少有一个映射的 operation，未映射项明确排除，不由 AI 猜测关系。
- Schemathesis 通过 `--include-operation-id` 只运行映射接口；默认成熟阶段保持 examples、coverage、fuzzing、stateful，固定单 worker、deterministic、zero retry。
- Schemathesis 从 4.24.3 升到 4.29.3；本机补齐官方 uv 0.13.0 / `uvx`。Windows Runner 强制 UTF-8，修复 GBK 终端对 Schemathesis Unicode 输出导致的真实崩溃。
- 新环境先执行 `npm run setup:api`：脚本只接受 Python 3.12，固定安装 uv 0.13.0 并预热 Schemathesis 4.29.3；版本或安装失败会停止，不自动改用全局 Schemathesis/Python SDK。
- SQLite 历史 OpenAPI 数据不自动迁移到新业务链路；缺少 Approved 版本的旧记录不能运行，需重新导入。旧需求/证据关联不再被产品入口读取。
- Infisical adapter 边界已保留但未伪造连接状态；正式接入必须先具备可运维实例、Machine Identity 和真实项目/环境，再用官方 SDK/API 读取运行期密钥。
- API 自动化页拆为“契约生成测试 · Schemathesis”和“业务场景执行 · Hurl”。Hurl 场景必须使用 `{{baseUrl}}` 绑定所选项目环境，并至少关联一条 Approved TestCase；写死目标 URL 或保存明文敏感 Header 会被拒绝。
- Bearer/Basic 凭证只通过 Hurl 运行时环境变量注入，子进程关闭 shell、限制输出和运行时长，保存日志前再次脱敏。场景集、Approved TestCase 映射、JUnit 结果和 Runner 版本形成独立证据链。
- 新环境执行 `npm run setup:hurl`，只从官方 8.0.1 release 下载 Windows 二进制并校验 SHA-256；不使用 npm 安装器和全局 Hurl。

## 受控真实验收

- 命令：`npm run test:at01`。
- 本地启动真实 HTTP 目标，导入 OpenAPI 3.0.3，映射 `getItem` operation 到受控 Approved TestCase ID。
- 使用真实 `uvx schemathesis@4.29.3` 执行；受控目标返回 HTTP 500，TestRun 状态 `failed`，生成 2 个 examples，保存 2 个失败项并回链已映射 operation。
- 第一次执行真实暴露 Windows GBK `UnicodeEncodeError`，修复运行环境后同一命令通过。没有 fallback、假结果或静默重试。
- 命令：`npm run test:hurl`。本地真实 HTTP 服务执行两步 Hurl 链路：第一步捕获 `item_id`，第二步使用该变量查询；2 次请求及 JSONPath 断言通过，JUnit 保存 1 个通过场景，并保留 2 条 Approved TestCase 关联。

## 当前阻塞边界

用户提供的 16 页售后 PRD 没有 OpenAPI 契约、目标 Base URL、认证方式或可测试服务。不能把 72 条业务用例自动猜成接口，也不能用受控 fixture 冒充业务验收。取得真实 OpenAPI 与测试环境后，从 Approved v1 映射真实 operation 并执行，才能完成 AT01 业务验收。
