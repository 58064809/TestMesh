# FR01 — 形式化需求验证

> **已撤回（2026-10-08）**：该探索把候选工具错误实现成第二套需求分析产品路径，偏离“单一 AI 需求分析入口”和 Agent / AI 应用质量保障目标。页面、API、存储、运行时与测试已删除；本文只保留调研证据。TLA+ 未来只有在具体 Agent 质量场景证明必要时才重新评审。

## 目标

把已人工确认的需求基线映射为可审阅的 TLA+ 模型，并由官方 SANY/TLC 命令行工具做确定性语法与有限状态模型检查。TestMesh 不实现状态空间搜索、时序逻辑求值或冲突算法。

## 调研与选型

- **选定：TLA+ CLI / TLC 1.7.4**。官方工具链、MIT 许可、Java 11+；固定使用 `tla2tools.jar`，不依赖已无人维护的 Eclipse Toolbox。
- **不选 FRET 作为中文入口**：FRET 3.0 能做受限英语需求、形式化、冲突分析和测试生成，但其核心入口是 restricted English，不能直接承担中文需求主链路。
- **不选 Apalache 作为第一版执行器**：它是 TLA+ 的 SMT/符号模型检查器，擅长更大或含整数时钟的状态空间，但有独立的受支持语法子集和运行栈。当前再并行维护会违反 Single-path MVP。
- **不选 Alloy**：更适合有限范围内的结构关系模型查找，不是本阶段状态/时序验证的单一路径。

## 已实现边界

1. 页面只能选择不可覆盖的 Requirement Baseline，并只能关联该基线中已接受的 Requirement ID。
2. 第一版接收经人工审阅的 `.tla` 和 `.cfg` 内容；审阅人及确认框必填。没有人工审阅不能执行。
3. 使用参数数组直接启动项目本地 Java，不经过 shell；模块名受限，输入大小、超时、最大堆和输出大小有硬限制。
4. 固定使用 SANY/TLC 单一路径、单 worker 和 tool mode。成功、违反、运行错误、超时分开记录，不切换引擎。
5. PostgreSQL 保存需求基线、Requirement ID、模型、配置、审阅人、工具版本、退出码、耗时、完整 stdout/stderr，并把稳定版 TLC tool-mode 反例输出封装为 JSON 证据。
6. UI 明确提示：TLC 通过只表示在本次模型与有限状态空间内没有发现违反，不证明自然语言需求天然正确。

## 企业边界与后续

- 当前闭环是“导入/人工审阅模型 → 确定性验证 → 证据留存”。中文 RequirementAnalysis 自动生成 TLA+ 仍属于候选生成能力，不能绕过人工语义审阅；在没有真实企业模型样本验收前不宣称自动转换可靠。
- 对大状态空间，如 TLC 资源边界成为真实瓶颈，再以实测数据评审 Apalache；当前不预装、不保留 fallback。
- 模型检查是设计验证证据，不替代测试、代码验证或生产监控。

## 验收

- 工具版本和哈希检查通过。
- 正确模型返回 `passed` 和退出码 0。
- 故意违反不变量的模型返回 `violated`、非零退出码并产生可读反例。
- 非法模块名、模块名不一致、空配置、非基线 Requirement ID、未确认人工审阅均被拒绝。
- 自动测试、lint、TypeScript 和 production build 全部通过。
