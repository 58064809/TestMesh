# FT01 — 自动化失败智能诊断与辅助缺陷定位

## 1. 目标与边界

FT01 不是独立缺陷录入产品，而是 API/UI 智能化执行的下游诊断节点。唯一主链路为：

`AI 需求分析 → Approved TestCase → API/UI 脚本与执行 → 失败断言 → 智能诊断与链路追踪 → 缺陷草稿`

TestMesh 从失败 TestRun 自动取得 Approved TestCase、执行步骤、预期、请求响应、断言、Runner 和 Trace；再按故障信号查询业务系统可观测数据、只读数据库/中间件结果和对应版本源码，生成一份**有证据的缺陷定位草稿**。测试人员不重复填写标题、步骤、预期和实际结果。

该能力用于缩短排查路径，不代替研发确认根因，不自动修改代码、数据库或缺陷系统，也不把模型猜测写成确定事实。

首版完成标准：从一次真实失败 TestRun 出发，至少定位到故障层级和候选服务/组件；只有存在调用栈或源码引用时，才允许定位到文件与行号。

## 2. 为什么不能只把日志交给大模型

缺陷定位需要回答五个不同问题：

1. 测试到底在哪里失败：TestRun、步骤、请求响应、截图、Playwright Trace。
2. 请求经过了什么：Trace、错误 Span、服务拓扑、上下游依赖。
3. 系统当时发生了什么：与 Trace ID、时间窗口和服务关联的日志、异常栈和指标。
4. 数据是否符合业务预期：受治理的只读查询结果，而不是让 Agent 任意访问数据库。
5. 哪段实现可能导致现象：与部署版本一致的源码、Commit、配置和调用栈。

缺少关联 ID、时间范围、服务版本或 Commit 时，跨数据源拼接容易产生伪定位。因此 TestMesh 必须先建立证据关联，再让 Agent 推理。

## 3. 成熟能力调研结论

| 能力层 | 选择 | 复用内容 | TestMesh 只保留 |
| --- | --- | --- | --- |
| 业务系统遥测标准 | OpenTelemetry | Trace/Span、日志关联、资源和异常语义、OTLP Collector | `test_run_id`、`testcase_id` 等业务关联属性约定 |
| APM 与全链路查询 | Apache SkyWalking + BanyanDB | Trace、日志、指标、拓扑、Profiling、存储和 UI | 项目级连接配置和证据引用 |
| Agent 查询 SkyWalking | Apache SkyWalking MCP | `query_traces`、`query_logs`、指标和拓扑查询工具 | 工具白名单、任务上下文和查询审计引用 |
| 数据库诊断 | 本地受控验收使用 DBHub；企业接入使用 Bytebase MCP | PostgreSQL/MySQL/SQL Server 等查询；企业版治理、脱敏、审计和权限 | 数据源绑定、只读策略 ID、查询证据引用 |
| 源码检索 | 本地 Git 使用 Deep Agents 只读文件后端；GitHub 使用官方 GitHub MCP read-only；多仓企业可配置 Sourcegraph MCP | 文件读取、代码搜索、提交与版本上下文 | 仓库与部署 Commit 绑定、源码引用 |
| 调查 Agent | 现有 Deep Agents / LangGraph Harness | Agent Loop、工具调用、权限和结构化输出 | FailureTriage Schema、完成门和人工确认 |
| Agent 可观测与评测 | 现有 OpenTelemetry + OpenInference + Phoenix | Agent Trace、Token、耗时、Dataset、Experiment、Evaluator | 缺陷任务 ID、证据 ID、评测标签 |

### 未选择的方案

- **Sentry Seer**：能力成熟，能结合 Issue、Trace、日志、Profile 和 GitHub 源码做根因分析及修复；但会把首版绑定到 Sentry 商业数据面，和“可私有部署、可接公司既有 APM”的目标不符。
- **OpenHands**：适合自主软件工程任务，但会在现有 Deep Agents 之外引入第二套 Agent Harness。FT01 只需要受控只读调查，不需要另建编码 Agent 平台。
- **自研日志、Trace、数据库或代码搜索平台**：明确禁止。TestMesh 只消费成熟系统提供的查询工具与证据。

## 4. 推荐架构

```text
失败 TestRun（已关联 Approved TestCase）
            │
            ▼
   TestMesh Failure Evidence Bundle
   - project / environment / version
   - testcase / steps / expected / actual
   - request / response / screenshot / trace.zip
   - trace_id / time window / commit SHA
            │
            ▼
   Deep Agents Failure Triage Agent
      ├─ TestMesh 测试证据（只读）
      ├─ SkyWalking MCP（Trace/日志/指标/拓扑，只读）
      ├─ Bytebase/DBHub MCP（按需，只读、限时、限行）
      └─ Git/ GitHub/Sourcegraph（与部署版本一致，只读）
            │
            ▼
   FailureTriage 结构化结果
   - 已确认事实与 evidence_refs
   - 故障层级和候选组件
   - 候选原因、反证、置信度
   - 仍缺少的证据和下一步检查
   - 可提交的缺陷标题、复现、实际/预期结果
            │
            ▼
       人工确认后复制/提交
```

Phoenix 记录的是“缺陷定位 Agent 如何使用工具和形成结论”；SkyWalking 记录的是“被测业务系统发生了什么”。两者职责不同，不能互相替代。

## 5. 调查策略

Agent 不应每次查询全部数据源，而应采用证据驱动的最小路径：

| 失败现象 | 首查 | 满足条件后再查 |
| --- | --- | --- |
| HTTP 5xx、超时 | 请求响应 → Trace 错误 Span → 关联日志 | 异常栈对应源码；怀疑数据时只读查库 |
| HTTP 4xx、业务拒绝 | 请求参数、鉴权信息、契约和业务规则 | 网关/服务日志；必要时查询业务状态 |
| 页面断言失败 | Playwright Trace、截图、DOM、网络请求 | 前端源码；若接口异常再沿后端 Trace |
| 数据不一致、状态未更新 | 业务步骤、接口结果、Trace 中 DB/MQ Span | 只读查库、消费日志、事务/重试源码 |
| 环境或依赖异常 | 拓扑、指标、实例/容器日志、部署事件 | 配置仓库和基础设施证据 |
| 自动化脚本误报 | Runner 输出、Trace、定位器、重试记录 | 测试源码；不得误判为产品缺陷 |

数据库查询不是默认步骤。只有现有证据指向数据状态、事务、缓存或消息一致性时才启用；生产或共享测试库必须由 Bytebase 一类治理层提供只读账号、对象范围、脱敏、行数限制、超时和审计。

## 6. FailureTriage Schema

```text
FailureDiagnosisRequest
  run_kind, run_id             # 页面只提交执行引用

FailureDiagnosisContext        # 服务端从 TestRun 追溯关系解析，客户端不能指定
  project_id, environment_id, run_kind, run_id
  approved_version_id, approved_testcase_ids[]
  evidence[]                   # Approved TestCase、断言、请求响应、Runner、Trace 等

FailureTriage
  status: located | suspected | insufficient_evidence
  failure_layer: test_script | frontend | gateway | backend |
                 database | cache | message_queue | third_party |
                 environment | unknown
  suspected_components[]
  facts[]                 # 必须引用 evidence_refs
  hypotheses[]            # 原因、支持证据、反证、置信度
  source_locations[]      # repository, commit, file, line；证据不足则为空
  database_findings[]     # 脱敏 SQL/模板、结果摘要、数据源证据 ID
  missing_evidence[]
  next_checks[]
  submission_draft        # 标题、严重程度建议、复现、实际/预期、附件清单
  observability           # Phoenix trace reference
```

确定性完成门：

- 每条事实至少有一个真实 `evidence_ref`。
- `located` 必须引用调用链/日志、数据库、中间件或源码定位证据；仅有 TestRun、失败断言或 HTTP 500 只能返回候选。测试脚本定位还必须由 Runner/Trace 与脚本源码相互印证。
- 文件与行号必须来自与部署 Commit 一致的源码工具结果。
- 所有数据库结论必须带查询证据，敏感字段不得进入模型上下文和结果。
- 证据不足时只能返回 `suspected` 或 `insufficient_evidence`。
- Agent 不得执行写库、修改源码、重启服务或自动提交缺陷。

## 7. 项目配置

项目配置新增“缺陷定位数据源”，而不是在缺陷页面重复填写：

- 可观测性：SkyWalking MCP URL、认证引用、健康状态。
- 源码：本地 Git / GitHub MCP / Sourcegraph MCP 三选一，绑定仓库和部署 Commit 获取方式。
- 数据库：关闭 / DBHub（仅本地验收）/ Bytebase MCP 三选一，绑定只读数据源与策略。
- 关联字段：HTTP 响应头 Trace ID、日志 Trace 字段、环境/服务/版本属性名。

首版只实现本地 Git + SkyWalking MCP + DBHub 受控演示这条路径；GitHub、Sourcegraph 和 Bytebase 是相同 MCP 接口下的企业配置替换，不并行实现三个专用客户端。

## 8. 实施与验收顺序

### FT01-A：执行结果内嵌诊断闭环（已完成重构）

1. 定义 Schema、完成门和执行结果内嵌诊断组件。
2. 复用已有失败 API/UI TestRun、Approved TestCase、断言、请求响应和 Playwright Trace。
3. 证明 Agent 能区分产品缺陷、测试脚本问题和证据不足。

2026-10-14 验收记录：

- 2026-10-15 用户纠偏：此前“独立缺陷定位入口 + 手填缺陷表单”的产品形态不符合主链路，已撤回。左侧独立入口与手工表单已删除。
- 诊断入口只出现在失败的 Schemathesis、Hurl 和 Playwright TestRun 中；请求只包含 `runKind + runId`，项目、环境、Approved TestCase、预期、实际和断言证据均由服务端追溯。
- 失败 TestRun 对应的冻结 Approved TestCase 已作为直接证据进入 Agent；不存在关联时明确停止，不让用户手工补写成事实。
- 已使用真实失败 UI TestRun `86f4880e-97fa-403f-9225-83ed08274a85` 发起真实模型分析并持久化结果 `a6edc607-1379-448b-b07e-7634f09a6e51`。
- 两个 Playwright 用例分别等待“订单号”和“提交申请”控件 30 秒超时。Agent 正确返回 `suspected / unknown`，提出前端未渲染、定位器不匹配和环境/路由异常三类候选，并明确列出 Trace、Error Context、源码和日志等缺失证据；未伪造后端、数据库或代码根因。
- Phoenix Agent Trace：`97458b77d532f798859cb18ff689f94c`；本次使用 5,847 tokens。
- FailureTriage 完成门拒绝不存在的证据引用、无源码证据的文件/行号、无数据库证据的数据库结论，以及证据不足却声明 `located` 的结果。
- 重构后 21 个测试文件、104 项测试通过；lint 和生产构建通过。原 FT01-A 模型结果仅作为旧形态技术验证记录，不作为当前产品形态验收结果。

### FT01-B：受控全链路验收

1. 使用 Docker Compose 启动官方 SkyWalking OAP、BanyanDB、UI 和 SkyWalking MCP。
2. 为受控 API 目标接入 OpenTelemetry，注入一个已知后端故障，保留 Trace、日志和版本属性。
3. 通过 LangChain 官方 MCP Adapter 把 SkyWalking 工具交给现有 Deep Agent。
4. Agent 应定位到正确服务/错误 Span，并引用 Trace 与日志证据。

当前阻塞（2026-10-15）：Docker Desktop 4.95.0 与 WSL 2 组件已安装，但 Windows 标记 `RebootPending`，容器引擎必须在重启后启动。按照禁止静默降级规则，未使用 mock、其他 APM 或临时自研查询接口替代。重启后继续 SkyWalking 受控全链路验收。

### FT01-C：只读数据库与源码验收

1. 使用 DBHub 连接隔离的演示数据库，强制 read-only、超时和行数限制。
2. 将部署 Commit 与本地 Git 仓库绑定，只开放读取和搜索。
3. 注入一个已知数据/代码缺陷；Agent 应按需查询数据库并定位到正确候选代码，不能执行任何写操作。

### 验收指标

- 已知故障层级命中率：受控样本 100%。
- 已知服务/组件命中率：受控样本 100%。
- 无证据事实率：0%。
- 错误根因确定化率：0%。
- 非必要数据库查询率：0%。
- 写操作暴露数：0。
- 每次结果可回链 TestRun、遥测/查询/源码证据和 Phoenix Agent Trace。

## 9. 评审决定

推荐批准以下单一路径：

**OpenTelemetry → SkyWalking/BanyanDB → SkyWalking MCP → LangChain MCP Adapter → 现有 Deep Agents；数据库通过 DBHub/Bytebase MCP 只读接入；源码通过只读 Git/MCP 接入。**

方案已于 2026-10-14 获用户批准并开始实施。FT01-A 已完成；下一步为 FT01-B 的 SkyWalking 受控全链路验收。
