# HR01 — AI 候选稿人工修正与冻结

## 目标

TestMesh 的 LLM 产物不能只有“接受/驳回”。统一生命周期为：

`AI 候选稿 → 人工修正 → 确定性校验 → Diff/修正记录 → 人工批准 → 冻结版本`

已冻结的 Requirement Baseline 和 Approved TestCase 不可覆盖；后续变化必须产生新候选和新版本。

## 当前实现（2026-10-15）

### 需求分析

- 在现有人工评审弹窗内修正条目描述和真实原文引用。
- 修正与评审在同一 PostgreSQL 事务中保存。
- 修正只能引用当前分析中真实存在的 source ID。
- 修改内容时评审人和修改理由必填。
- `analysis_amendment_events` 保存修改前、修改后、修改人、理由和时间；评审历史展示完整 Diff。
- 已建立 Requirement Baseline 的分析继续只读。

### 测试用例

- 在 TestCase 评审弹窗内修正标题、模块、测试目标、优先级、前置条件、测试数据、步骤/预期和中文 Gherkin。
- 保存时重新执行 TestCase Schema、Cucumber/Gherkin、追溯、TestCondition 和全局覆盖率 Gate。
- 修正与评审在同一 PostgreSQL 事务中保存；失败时两者均不落库。
- `test_case_amendment_events` 保存修改前、修改后、修改人、理由和时间；用例详情展示 Diff。
- Approved TestCase 继续不可覆盖。

### API/UI

- 后续生成脚本必须直接复用该生命周期：生成候选脚本、人工修正、成熟 Runner 校验、批准后执行。
- 页面上传 OpenAPI/Hurl 的入口已经移除；已有契约、脚本及执行后端暂时保留，用于承接后续“项目知识发现 → AI 生成 → 人工修正 → 审核 → 执行”的正式链路，不再作为用户主入口。
- 搭架阶段允许使用隔离且显著标识的演示数据验证生成/修订界面；功能验收前必须删除假数据路径，不能写入正式业务结果。

## 验证

- PostgreSQL 启动迁移已建立两类 amendment event 表。
- 现有 1 份已冻结需求分析和 1 份已批准测试设计均可正常读取，修正记录为 0，原数据未改变。
- 21 个测试文件、105 项测试通过；lint 和生产构建通过。
