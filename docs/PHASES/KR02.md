# KR02 — 项目知识混合检索

## 目标

在现有 Docling、PostgreSQL、OpenAI Embedding 和 Qdrant 单一路径上补齐可用于需求与测试建模的成熟混合检索，不建设第二套 RAG 平台。

## 框架评审结论

- LlamaIndex.TS 和 Haystack 都提供完整 RAG Pipeline、Retriever、Ranker 与评测能力，但引入任一框架都会与 TestMesh 已采用的 LangChain/Deep Agents、Docling、Qdrant 和 Phoenix 形成平行工作流与评测面，本阶段不集成。
- Ragas 提供 Faithfulness、Context Recall 等成熟指标，但 TestMesh 已确定 Phoenix 为 Dataset、Experiment、Trace 和 Evaluator 的唯一平台；本阶段不增加第二套评测运行时。
- Qdrant 1.20 正式提供基于全文索引的 BM25 评分，并能通过 Query API 将 BM25 与 Dense 查询进行原生 RRF 融合，直接复用现有 payload 与向量，是当前最小且成熟的集成方案。

## 唯一实现路径

`项目绑定且已索引的文档 → Docling/结构化 JSON 分块 → text-embedding-3-small Dense 向量 → Qdrant multilingual BM25 全文索引 → Dense + BM25 候选 → Qdrant 原生 RRF → 带 chunk/source 定位的证据`

- Qdrant Server 固定为 `1.20.1`，Windows 官方包使用 GitHub Release 提供的 SHA-256 校验；JS 客户端固定为 `1.20.0`。
- `text` payload 使用 Qdrant `multilingual` tokenizer 和 BM25 scoring，不在 TestMesh 内实现分词、BM25 或 RRF。
- `document_id` 建立 keyword payload index；模型生成只检索当前项目显式绑定且状态为 `indexed` 的文档，不再对所有项目知识做全局召回。
- PostgreSQL 继续保存原文件、SHA-256、索引状态和项目绑定；Qdrant 只保存可重建检索索引。
- 检索候选深度暂定为最终 Top-K 的四倍且不少于 20，RRF 使用 Qdrant 默认参数。没有标注集前不手调权重。

## 真实验收

2026-11-17 从 Qdrant `1.19.2` 升级到 `1.20.1` 前，为 `testmesh_knowledge` 创建快照 `testmesh_knowledge-965817416810689-2026-11-17-02-54-35.snapshot`，大小 348,400,128 字节，SHA-256 `c902482d4464af8ad200a8087b78622b83892a064a4bd716ba0b5197742b1fbc`。

升级后原集合状态为 `green`，5 个点均保留；`text` multilingual BM25 与 `document_id` keyword 索引创建成功。真实 Query API 以 Dense 和 BM25 两路 prefetch、RRF 主查询返回 5 条结果，首条为真实 chunk，证明不是单元测试模拟。

## 当前边界与下一步

- 本阶段只完成检索，不将检索结果直接视为业务真值；Agent 仍必须保存 chunk 快照并接受来源与追溯门禁。
- 尚未建立带相关 chunk 标注的检索 Dataset，因此不能宣称 Recall@K、MRR、nDCG 已达标，也不引入 Cross-Encoder Reranker。
- 下一步先在 Phoenix 建立项目级检索评测 Dataset，比较 Dense、BM25 和 Hybrid RRF；只有数据证明仍有排序缺口时，才评审 Qdrant 多阶段 ColBERT 或成熟 Reranker。
