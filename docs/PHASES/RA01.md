# RA01：基于 Harness 的需求分析

- **状态**：已完成
- **开始日期**：2026-09-17
- **完成日期**：2026-09-17
- **前置阶段**：H00 已完成

## 目标

把当前需求分析原位迁移为第一个正式 Stage Profile，使多文件和图片来源、固定 RequirementAnalysis Schema、引用校验、人工评审、决策回写和 Requirement Baseline 统一运行在 H00 Harness 上。

## 单一路径

```text
Task Manifest
  → Requirement Analysis Stage Profile
  → Source Reader / Locator
  → LangChain Agent + Deep Agents Skill Middleware
  → 固定 RequirementAnalysis 候选 Artifact
  → Schema / Source / Conflict Completion Gate
  → 人工 Review 与决策回写
  → Requirement Baseline
```

## 固定输出协议

RequirementAnalysis 顶层只包含：

```text
summary
requirements[]
actors[]
business_rules[]
flows[]
states[]
constraints[]
exceptions[]
open_questions[]
sources[]
```

公共 `origin` 只允许 `explicit/inferred`；`open_questions[].issue_type` 只允许 `missing/ambiguity/conflict`。没有内容时保持 `null` 或空数组，不为满足模板编造内容。Risk 和 TestCase 不属于本阶段。

## 实施顺序

1. 固定 Requirement Analysis Stage Profile。
2. 把现有多文件、PDF 页面图、独立图片和补充资料读取能力迁入受控 Tool。
3. 用 LangChain Agent 原位替换旧 Responses API 直调入口。
4. 把 Schema、来源存在性、图片/页码定位和冲突双证据接入 Completion Gate。
5. 把人工 Review、问题决策、获批 PRD 和 Baseline 接入 PostgreSQL 业务表与 LangGraph 恢复点。
6. 一次性迁移仍有效的数据或明确清理无效旧数据，同一变更删除 SQLite 业务路径和旧直调代码。

## 明确不做

- 不生成 Risk、Test Point、TestCase 或自动化代码。
- 不接入 RAG；当前没有 RAG 时不伪造知识命中。
- 不恢复飞书入口；权限问题继续搁置。
- 不启用异步子 Agent、Interpreter、Shell、写文件或未在 Profile 声明的 Tool。
- 不创建新版本接口，不保留 SQLite/PostgreSQL 双读写或旧协议兼容分支。

## 验收标准

1. Stage Profile 固定声明 Context、Knowledge、Skills、Tools、Policy、Schema 和完成条件。
2. 文本、PDF 页面图、独立图片和补充资料进入同一任务，且每个来源保留文件与定位信息。
3. 输出只来自固定 RequirementAnalysis Schema；来源无效、冲突证据不足或重要结论无来源时不能完成。
4. 人工 Review 可以驳回、合并、待澄清或接受；只有保留项进入评审与 Baseline。
5. 问题决策、决策人和获批 PRD 版本完成回写后才能冻结 Baseline。
6. 中断后可从 PostgreSQL Checkpoint 恢复，业务事实只从 PostgreSQL 业务表读取。
7. 旧入口和旧持久化路径在同一切换中删除；自动检查及真实多模态验收通过。

## 当前实现与验收记录

- Requirement Analysis Stage Profile 已固定声明 Context、Knowledge、Skills、Tools、Policy、Schema 和完成条件；未声明能力不会进入阶段运行环境。
- Agent 使用 LangChain `createAgent` 与 Deep Agents 渐进式 Skill 中间件，结构化输出由固定十字段 Schema 约束；旧 OpenAI Responses API 直调函数及其直接依赖已删除。
- Source Reader 统一处理文本、PDF、独立图片和补充资料；Checkpoint 只保存任务、分析与基线 ID，不保存文件字节。
- Completion Gate 已覆盖 Schema、引用存在性、来源定位、冲突双来源和来源优先级证据；Agent 自报完成不能绕过确定性判定。
- 人工评审、追加式评审事件、问题决策、获批 PRD 和不可覆盖 Baseline 已落入本机 PostgreSQL `testmesh_business` Schema；LangGraph 在人工评审处暂停，建立基线后从 PostgreSQL Checkpoint 恢复。
- 已将唯一有效分析 `717ee21b-4428-4da1-b5ae-455a6dfd1569`、原文件、72 条评审历史和 Baseline v1 一次性迁入 PostgreSQL；旧协议分析未迁移，SQLite 需求分析数据及专用表已清理。其他历史模块的 SQLite 数据未改动。
- 本机 PostgreSQL 集成测试已验证分析、来源文件、追加式评审、基线和工作流恢复。页面已读取迁移后的唯一报告与冻结基线，没有保留 SQLite/PostgreSQL 双读写。
- 2026-09-17 首次新 Harness 真实多模态验收已完成模型调用、固定 Schema 解析和领域校验，并进入 Completion Gate；一次性验收脚本在输出报告时误读不存在的 `criteria` 字段，未保留 Gate 的最终通过状态和统计，因此不能据此把 RA01 标记完成。该请求没有写入正式分析、评审或基线，也没有自动重试。
- 经用户批准的第二次真实请求读取了同一份 16 页 PDF，约两分钟后返回；候选结果包含未写页码的 PDF 图片定位，被来源校验拒绝，未保存业务数据。根因是旧 Structured Output 只声明 `locator` 为字符串，页码约束只存在于提示词和事后校验。现已按当前任务来源动态生成 Source Schema：PDF 的正文和图片定位在模型输出阶段就需要带页码，文本只允许段落定位，独立图片只允许图片定位，未知来源 ID 也不能进入候选结果；事后校验继续作为 Completion Gate 防线。修复已通过定向类型检查和 15 项相关测试，尚未再次发送付费请求。
- 经用户再次批准，修复后的新 Harness 真实多模态验收约两分钟完成。模型从同一份 16 页 PDF 生成 17 项需求、5 个角色、11 条业务规则、6 条流程、8 项状态、5 项约束、5 项异常、9 个待确认问题和 22 条原文来源，其中 4 条为带页码的 PDF 图片证据；输入 98,226 tokens，输出 8,023 tokens，总计 106,249 tokens。
- `schema_valid`、`references_valid`、`source_locations_valid`、`issues_valid`、`source_priority_valid` 五项 Completion Gate 全部通过。真实候选只用于隔离验收，没有写入正式报告列表；生产 PostgreSQL 仍保留唯一有效分析、完整评审历史和 Baseline v1，避免产生无业务用途的第二版本。
- 最终自动验收结果：60 项测试通过，lint 通过，客户端与服务端 build 通过，Harness 与 Requirement Analysis 两条 PostgreSQL 集成验收通过。RA01 验收完成。
