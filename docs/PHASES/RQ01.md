# RQ01 — 成熟需求语言质量能力接入

## 目标

把模糊表达、被动语态、缺少主体、不可验证性、复合需求和术语一致性检查交给成熟的需求质量产品。TestMesh 只负责提交已提取的需求文本、保存外部分析结果与版本信息、关联原文来源，并提供人工接受、驳回和处置记录；不自研词典、句法规则或评分算法。

## 选型调研（2026-10-07）

| 候选 | 已确认能力 | 结论 |
| --- | --- | --- |
| QVscribe / QRA Platform | 面向需求工程的确定性 1–5 评分；19 类清晰度、可测试性、结构和一致性检查；问题定位到触发文本；支持 EARS、INCOSE、自定义配置与术语表；提供 REST WebAPI、Cloud、私有云和本地部署方向；产品仍持续发布 | **首选**。能力与 TestMesh 边界最匹配，但 API 契约、认证和许可不公开，官方说明需联系 QRA 开通；公开资料未确认中文分析能力，不能在拿到租户与中文样本验证前编码或宣称支持 |
| IBM Engineering Requirements Quality Assistant | Watson NLP 需求评分，可识别复合需求、逃逸条款、不精确动词、缺主体/动作/对象、被动语态等 | 不选。官方明确只支持英文和 ASCII；3.x 已于 2026-07-31 进入 Sustained Support，不适合作为新系统核心能力 |
| LanguageTool | 成熟开源语法与风格检查器，可自托管 HTTP 服务；中文有基础支持 | 不选作本阶段主路径。它不是需求工程质量引擎，不能覆盖可验证性、完整主体、EARS/INCOSE 和需求级确定性评分；公共 API 也禁止自动化批量使用。不能用它冒充完整需求质量能力 |
| The REUSE Company Requirements Quality Analysis / SE Suite | 专业需求质量与系统工程套件，支持质量评估与集成 | 公开产品/API资料不足，无法确认当前可采购版本、中文、接口契约和最小独立部署；现阶段不优于 QVscribe |
| reqSuite rm | 需求管理平台内置智能辅助，可本地或 Azure 托管 | 能力面是完整 RM 平台而非可独立拼装的质量分析 API，引入范围过大 |

## 决策

选择 **QVscribe WebAPI** 作为唯一候选接入路径，不并行接入 IBM RQA、LanguageTool 或自写检查器。

选择依据：

1. 它是持续维护的专业需求质量引擎，而不是通用语法检查或通用大模型自评。
2. 评分是确定性的，结果包含规则、配置版本、引擎版本和触发文本，适合审计与人工复核。
3. WebAPI 直接支持 CI/CD 和第三方工作流，符合 TestMesh“只展示外部分析结果及人工处理”的边界。
4. IBM RQA 的英文/ASCII限制和生命周期状态不符合本项目；LanguageTool 的能力范围不足。

## 当前阻塞

截至 2026-10-07，QVscribe 官方公开资料只确认 WebAPI 托管在 QRA Cloud，并要求联系厂商讨论接入；没有公开可实现的端点契约、认证说明、测试租户或中文支持声明。因此本阶段停在外部准入点：

- 需要 QVscribe API 试用或正式租户；
- 需要厂商提供当前 API/OpenAPI 文档和认证方式；
- 需要确认数据驻留/私有部署要求；
- 需要用中文需求样本验证语言支持。若不支持中文，必须回到选型决策，不能私自补一套中文规则或以通用模型评分替代。

在这些条件满足前，不新增 API 适配器、数据库表或页面，不删除现有需求分析能力，也不使用 mock 伪造验收。

## 获得准入后的单一路径

`已提取 Requirement + 来源引用 → QVscribe WebAPI → 原样保存评分、问题、触发文本及引擎/配置版本 → TestMesh 展示 → 人工接受/驳回/备注`

## 验收标准

1. 使用真实租户对至少一条清晰需求和一条有缺陷需求完成调用。
2. TestMesh 展示外部原始分数、规则类别、触发文本、建议和版本，不重新计算分数。
3. 每项结果回链 Requirement 与原文来源，并可保存人工处理记录。
4. 服务不可用、返回不完整或语言不受支持时立即失败，无本地规则或模型 fallback。
5. 测试、lint、类型检查和生产构建通过。
