# TD01 — 智能化测试设计与 TestCase

## 状态

进行中。2026-10-09 用户完成真实需求评审并建立 Baseline v1，明确批准开始本阶段。首个真实候选暴露出“覆盖矩阵通过但测试粒度过粗”的质量缺陷，已被用户拒绝作为验收成果。当前正在以原子 TestCase、专业 Skills、完整 PRD 输入和通用知识检索重构生成路径。

## 质量问题与输入边界

- 解决的问题：已批准需求难以系统转换为风险、测试点和可执行规格，容易遗漏异常、边界、规则分支和状态路径。
- 唯一输入：不可覆盖的 Requirement Baseline；不读取候选分析，不绕过人工评审，不重新解释被驳回条目。
- 产物：独立的 TestDesign、Risk、TestPoint、TestCase 结构化数据，以及可由成熟工具消费的中文 Gherkin。
- TestMesh 只保留业务 ID、追溯关系、人工评审和版本；不实现测试生成算法、Gherkin 解析器、组合覆盖算法或状态路径算法。

## 2026-10-09 调研与单一路径

### 立即接入

1. **Deep Agents `createDeepAgent`**：继续作为唯一 Agent Harness，负责受控结构化生成；不创建第二套 Agent Loop。
2. **Cucumber/Gherkin + `@cucumber/gherkin`**：作为业务场景与 TestCase 的标准表达和官方语法校验器。采用 `# language: zh-CN`，使用 `功能 → 规则 → 场景/场景大纲`，并用标签保存 requirement/risk/test-point ID。
3. **ISTQB 风险测试与测试设计技法**：只作为方法定义。Agent 选择场景、等价类、边界值、判定表或状态迁移时必须说明适用理由；TestMesh 不自研这些算法。
4. **Deep Agents 原生 Skills**：测试分析规划、场景、等价类/边界值、判定表、状态迁移、失败模式和跨系统一致性各自作为渐进加载的专业 Skill；Skill 可带参考材料，不创建第二套提示词编排器。

### 条件满足才调用

- **fast-check**：只有存在明确类型、范围或枚举约束时才生成 property/generator contract；真正执行放在后续自动化阶段。它负责 generator、constraint 和 shrinking，TestMesh 不枚举随机样本。
- **NIST ACTS**：只有存在两个以上有限参数域且约束完整时才生成 t-way 组合；缺少参数值或约束时不得猜测。
- **GraphWalker (Rust)**：只有存在可确认的状态、事件、起点和转移关系时才生成路径；不从模糊状态描述伪造完整状态机。优先采用其 JSON/MCP/CLI、覆盖停止条件和 requirement tracking。

条件未满足时，TestDesign 必须保存“不适用原因”，不得启用备用算法或静默退化为 AI 随机枚举。

### 通用 RAG 的边界与选型

- RAG 解决“PRD 之外的企业知识无法参与测试设计”，适用语料为架构说明、OpenAPI、数据字典、历史缺陷、运行约束和企业规则。
- 原始 PRD 与 Requirement Baseline 永远完整输入规划阶段；不得先切块检索再让若干命中片段代替全文。
- 文档分块复用 Docling `HybridChunker`，保留标题、表格及 provenance；向量检索复用 Qdrant，不自建向量索引、相似度算法或检索数据库。
- Agent 使用受限检索工具按测试条件补充证据；命中结果必须带知识文档、chunk ID、原文及定位。无知识库或无命中时明确记录，不允许模型伪造知识引用。
- 当前本机没有 Docker，Qdrant 采用官方 Windows 原生可执行文件的单机部署；生产迁移仍使用同一 Qdrant API，不保留另一套本地索引。
- Embedding 必须选成熟组件并完成中文检索样本验收。已排除当前 `fastembed-js` 路径：其传递 tokenizer 包已归档且本机安装长时间无法完成，不能作为到公司可用的唯一依赖。最终 Embedding 实现与检索评测完成前，RAG 状态仍是进行中。

## 第一条验收闭环

1. 选择已建立的 Requirement Baseline。
2. Agent 只读取该基线中的接受项、人工决策和原文引用。
3. 输出风险、测试点、覆盖说明和中文 Gherkin TestCase。
4. 服务端使用 Cucumber 官方解析器逐条校验 Gherkin；无效语法、无有效来源或无追溯关系时整体失败，不保存半成品。
5. 页面展示覆盖矩阵、风险、测试点、用例和原文追溯。
6. 人工接受、驳回或合并 TestCase；全部处理后形成不可覆盖的 Approved TestCase 版本。

## 不做

- 不从未基线化分析直接生成用例。
- 不自动批准、不写自动化代码、不执行 API/UI 测试。
- 不引入测试管理平台、第二个 Harness、备用模型或自研规则引擎。
- 不因为当前验收数据是占位内容而替用户修正业务决策。
