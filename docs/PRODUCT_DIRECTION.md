# TestMesh 产品方向

## 北极星

TestMesh 是 **Agent / AI 应用质量保障平台**，不是需求工程工具箱，也不是把成熟工具逐个做成页面的集成目录。

平台回答五个核心问题：

1. 本次发布的质量目标、范围、风险和责任人是什么？
2. 这个业务系统或 Agent / AI 应用应该做到什么？
3. 用哪些真实样本、测试用例和分层指标判断它做得好不好？
4. 本次运行发生了什么，失败证据在哪里？
5. 新版本是否退化，能否通过正式发布准入，问题如何进入持续改进？

## 唯一质量闭环

```text
项目与版本化质量计划
  → 质量目标、范围、风险、策略与发布门槛
  → 真实需求
  → 评估集 / 测试资产
  → 在成熟 Harness 中执行目标 Agent
  → 采集输入、输出、工具调用、Trace 与业务结果
  → 成熟 Evaluator / 测试引擎评分
  → 人工复核
  → 分层质量指标与回归比较
  → OPA 发布准入
  → 改进措施、验证证据与下一轮质量计划
```

## Testing for AI

智能测试设计既覆盖确定性业务行为，也覆盖 AI 系统行为。对 Agent、对话系统和生成式 AI，TestCase 至少按适用风险考虑意图识别、多轮上下文、约束保持、回复准确性、Groundedness/幻觉、安全拒答、工具选择与调用、鲁棒性与一致性。

AI TestCase 不以“让另一个模型看起来觉得不错”为验收标准。每条用例必须定义期望行为、oracle 类型、Evaluator、阈值、数据集要求和运行证据。执行和比较复用 Phoenix Dataset、Experiment、Evaluator 与 Trace；TestMesh 只维护 requirement/testcase/run/experiment 等业务 ID、人工修正、批准状态和准入事实。

## 项目质量管理主线

- **质量计划**：按项目和发布批次定义质量目标、ISO/IEC 25010 质量属性、AI 质量属性、范围、风险、策略、准入/准出条件、证据和批准人。
- **统一质量资产**：通过 ID/关系连接 Requirement Baseline、Approved TestCase、自动化 TestRun、Phoenix 评测与改进项，不复制 Runner 或评测平台的数据模型。
- **分层质量指标**：治理层、覆盖层、执行层、AI 质量层和持续改进层分别展示，避免不可解释的单一总分。
- **正式发布准入**：OPA/Rego 根据冻结计划和实时事实给出 allow/review/deny，保存策略与输入输出证据。
- **持续改进**：失败诊断、发布复核和复盘形成有负责人、期限和验证证据的改进项，并进入下一轮计划。

## 需求分析的边界

项目只有一个“AI 需求分析”入口。它只负责：

- 解析 PRD、Office、PDF、表格和图片；
- 找出缺失、歧义、冲突及不可验证内容；
- 给出准确原文引用；
- 支持人工确认并形成后续质量资产的可靠输入。

Docling 等成熟组件在后台工作，不单独成为业务模块。TLA+、DMN、FRET 等候选只有在具体 Agent 质量场景证明必要、且能被平台自动调用时才重新评审；不要求普通用户手写专业模型。

## Reuse-first 判定顺序

每增加一项能力都按以下顺序决策：

1. 先定义要解决的 Agent / AI 应用质量问题和可验收结果。
2. 调研成熟标准、开源项目和商业产品，不受推荐表限制。
3. 选择一条最小、可私有部署或满足企业数据边界的路径。
4. TestMesh 只实现成熟组件没有提供的业务映射、统一入口和证据关联。
5. 没有真实样本端到端验收，不进入产品导航和正式路线。

## TestMesh 应保留的能力

- 目标 Agent / AI 应用、版本和环境标识。
- requirement、dataset、case、run、trace、evaluation、artifact 的业务关联。
- 企业质量目标、评估配置、风险容忍度和准入策略。
- 跨工具统一入口、运行证据、历史比较与人工复核。

## TestMesh 不应自研的能力

- Agent Loop、Workflow Runtime、Checkpoint、Tool Executor。
- OCR、文档版面、浏览器/API/安全/性能 Runner。
- Trace 存储与通用 Eval 实验平台。
- 通用规则语言、模型检查器、测试管理系统或报告引擎。
- 已有成熟实现的生成器、组合覆盖、状态路径和测试结果格式。

## 当前纠偏

2026-10-08，用户确认推荐表只是候选清单，终极目标是 Agent / AI 应用质量保障。独立“形式化验证”和“业务规则”路径被撤回并删除；其调研结论仅作历史证据，不代表产品能力或后续承诺。
