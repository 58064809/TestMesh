# TestMesh Roadmap

## 状态定义

- `进行中`：唯一允许实施代码的阶段。
- `已规划`：只维护文档，不得提前实现。
- `已完成`：全部验收标准已验证并记录。
- `阻塞`：既定路径失败，等待用户决策；不得自行降级。
- `暂停`：用户明确要求先处理另一项已批准工作，原阶段不实施也不自动重试。

## P01 — 统一工作台与 PRD 多模态分析

- **目标**：让用户在统一中文工作台上传 PRD/截图并获得有证据的结构化需求分析。
- **范围**：Refine + Ant Design Shell、AI Chat、文本/图片/文件上传、最小 Project Knowledge、OpenAI Responses API、固定十字段 RequirementAnalysis、原文引用、页面报告与 Markdown 导出。
- **验收标准**：进入工作台 → 打开 AI Chat → 上传包含文本或图片的 PRD → 输入“帮我分析这个需求” → 获得通过固定 Schema 与来源校验的结果 → 查看原文引用并导出同源报告；定位不可靠时显式说明。
- **明确不做**：UI/API 自动化、知识库增强、长流程编排、后续引擎、模型 fallback。
- **依赖**：Node.js、Refine、Ant Design、OpenAI SDK、有效 `OPENAI_API_KEY` 与可用的单一模型。
- **下一阶段入口**：全部自动检查和一次真实多模态闭环通过，P01 标记已完成，用户批准继续。
- **状态**：旧版已于 2026-09-01 完成真实验收（15 条需求、10 条风险、10 个待确认问题、20 条证据；51,582 tokens）。新版协议修订进行中，旧分析已按用户要求删除；真实多模态请求的结构化结果被本地 PDF 图片定位判断拒绝，判断已修正但尚未获准重试，因此新版验收未完成。

## P02 — 领域模型与 API 测试闭环

- **目标**：建立 Requirement/Risk/Evidence/TestCase 数据模型并完成 OpenAPI 到 TestRun 的单一路径。
- **范围**：领域模型、OpenAPI 导入、Schemathesis 执行、结果与证据回写。
- **验收标准**：从 OpenAPI 生成并运行 Schemathesis 测试，TestRun 可追溯到 Requirement/TestCase/Evidence。
- **明确不做**：UI、APP、性能、安全测试；OpenHands 工程 Agent；复杂工作流运行时。
- **依赖**：P01 已完成；Schemathesis 可用；P02 数据模型 ADR 获批准。
- **下一阶段入口**：API 闭环验收通过并获得继续授权后进入 P03。
- **状态**：已完成。2026-09-01 使用有效 OpenAPI 和本地真实 HTTP 服务完成闭环验收；TestRun 保存 Schemathesis 失败的 operation、checks、request、response 与 reproduction。完整记录见 `docs/PHASES/P02.md`。

## P03 — OpenHands 与工程上下文

- **目标**：复用 OpenHands，把 Repo/Code/Log/Terminal/Docker 上下文接入 TestMesh。
- **范围**：OpenHands 集成、工程上下文选择与查看、分析任务的上下文关联。
- **验收标准**：用户可选择仓库并让 OpenHands 基于代码、日志、终端和 Docker 上下文完成批准的工程任务，结果可追溯。
- **明确不做**：自研 Agent Loop/Harness/Checkpoint；P04 测试引擎；P05 测试设计与用例生成；P06 质量门禁。
- **依赖**：P02 已完成；OpenHands 的部署与授权方案获批准。
- **下一阶段入口**：工程上下文闭环通过并获得继续授权后进入 P04。
- **状态**：已完成。2026-09-02 使用 OpenHands Agent Server 1.44.0 与 TypeScript Client 1.39.0 完成真实工程任务验收；Agent 在只挂载所选仓库的一次性 Docker 容器中执行 `pwd && git status --short --branch`，返回 `/workspace`、`## main` 和退出码 0。共保存 17 条真实 Agent Event、终端证据、最终结论、Token/Cost 与 Git Diff；未暴露 API Key，仓库无改动，容器已清理。详见 `docs/PHASES/P03.md`。

## P04 — 多类型测试引擎

- **目标**：扩展 UI、APP、性能和安全测试，并复用各自成熟引擎。
- **范围**：Playwright、Appium、k6、ZAP 的单一适配路径及统一 TestRun/Evidence 展示。
- **验收标准**：四类测试各有一条可运行、可追溯、失败透明的端到端路径。
- **明确不做**：重写引擎能力；并行引擎或备用 Runner；P05 测试设计与用例生成；P06 检索与 Quality Gate。
- **依赖**：P03 已完成；各引擎版本和部署方式逐项批准。
- **下一阶段入口**：四类路径全部验收并获得继续授权后进入 P05。
- **状态**：阻塞。P04-A Playwright、P04-B Android Emulator + Appium 和 P04-C k6 已完成真实闭环验收。P04-D 已获授权并完成最小代码与页面实现，但 ZAP 2.17.0 官方 Crossplatform ZIP 在 SHA-256 校验时被 Windows Defender 以 `Program:Java/Multiverze!rfn`（Threat ID `453479`，高危）拦截。文件未解压、ZAP 未运行；未经用户明确批准不得绕过防护、换包、改用 Docker/Installer 或进入 P05。详见 `docs/PHASES/P04.md`。

## P05 — 测试设计与用例生成

- **目标**：补齐 Requirement/Risk/Evidence → TestCase → 自动化代码 → TestRun 的可追溯闭环。
- **范围**：选择既有 Requirement、Risk 与 Evidence；复用 OpenAI Agents SDK 管理覆盖规划、分批生成和缺口复核，底层使用单一 Responses API 模型生成通用 TestCase；人工评审与明确批准；SQLite 持久化；统一既有 P02 API TestCase 的领域语义；复用 OpenHands 将批准用例落地为 Playwright 测试代码；复用 P04-A 固定 Docker Runner 执行；保存 TestCase、代码文件和 TestRun 的追溯关系。
- **第一版单一路径**：重新上传原始 PRD + 选择已保存的真实分析结果 → OpenAI Agents SDK 结合 PRD 多模态内容与 Requirement/Risk/Evidence 规划覆盖、分批提交用例并用确定性工具复核缺口 → 用户评审批准 → 用户授权 OpenHands 写入所选仓库 → 用户授权 Playwright Docker 执行 → 结果回链 TestCase 与原始证据。
- **TestCase 最小字段**：标题、测试类型、测试目标、前置条件、步骤、预期结果、优先级、Requirement/Risk/Evidence 关联、`draft/approved` 评审状态、自动化代码文件关联和 TestRun 关联。
- **验收标准**：使用真实 PRD 生成可追溯的结构化测试用例；未经批准的草稿不能进入代码生成；OpenHands 只根据批准用例生成一条 Playwright 测试；现有 P04-A Runner 成功执行；工作台可从 TestRun 反查 TestCase、Requirement、Risk 与 Evidence；失败时停在真实失败点且无 fallback。
- **明确不做**：自研 Agent Loop、自动批准、未经授权写代码或运行测试、自动 commit/push、多模型或多生成器、备用 Runner、API/APP/性能/安全测试代码生成、P06 检索/归因/门禁/CI。
- **依赖**：新版 P01 需求分析真实验收与后续 P05 测试设计协议调整；用户重新上传对应原始 PRD。用户已明确批准在 P04-D 下载与安全复核等待期间先执行 P05，但当前要求暂停 P05，先完成需求分析。该例外不允许绕过 P04-D 安全边界，也不允许提前进入 P06。
- **下一阶段入口**：P05 全部验收通过、记录完成且用户明确批准后进入 P06。
- **状态**：暂停。旧 13 条低覆盖草稿及其后的 15 条诊断草稿均已删除，生成型 TestCase 为 0 条。渐进式并行路径此前的首次真实请求停在来源规划把 R13、R14 同时放入生成分区与不适用项，没有自动重试。用户现在要求不保留旧分析并先完成新版 P01 需求分析；旧分析已删除，当前有 1 份新版分析，但 P05 尚未适配。P05 来源规划修正、测试风险识别及独立 TestCase Schema 重调均待用户后续决定。P04-D 继续保持阻塞状态。

## P06 — 质量治理与持续回归

- **目标**：把历史知识、失败归因和质量决策接入完整回归与 CI。
- **范围**：知识库、历史缺陷与用例检索、Failure Triage、Quality Gate、完整回归、CI。
- **验收标准**：一次 CI 回归可使用历史证据辅助归因，并输出可解释、可追溯的 Quality Gate 结果。
- **明确不做**：未批准的新测试类别、自研通用 RAG/Trace/Eval/Workflow 基础设施、平行实现。
- **依赖**：P05 已完成；检索和 CI 方案获批准。
- **下一阶段入口**：路线完成；任何新增阶段必须先更新 Roadmap 并获得用户批准。
- **状态**：已规划。
