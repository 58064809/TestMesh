# 智能导购系统业务需求基线 V1.0

> 文档类型：模拟业务获批 PRD  
> 业务名称：羽毛球拍智能推荐  
> 版本：V1.0  
> 状态：已评审通过，可作为测试设计基线  
> 批准角色：Product Owner（模拟业务）  
> 批准日期：2026-11-14  
> 适用范围：TestMesh 需求分析、业务建模、测试条件、TestCase、Dataset、Experiment 与 Evaluator 设计

## 1. 文档目的

本文档定义 TestMesh 模拟 AI 智能导购系统 V1.0 的正式业务需求与验收规则。

本文档是业务语义的唯一基线。需求分析、测试人员、自动化脚本、Dataset、Experiment 和 Evaluator 不得自行补充、放宽或改写本文档未授权的业务规则。

本文档描述的是**应实现、应验证的目标行为**，不代表这些能力已经开发完成，也不构成真实生产系统的发布证明。

## 2. 背景与目标

### 2.1 背景

TestMesh 需要一个边界明确、规则可验证、结果可复现的模拟 AI 业务，用于验证从需求到 AI 质量评测的完整工程链路。

### 2.2 产品目标

V1.0 提供羽毛球拍自然语言推荐能力，使用户能够通过单轮或多轮对话表达数量、价格、重量、品牌和颜色等条件。系统应完成意图识别、参数标准化、上下文管理、业务校验、商品查询、结果复核和最终回复。

### 2.3 验证目标

V1.0 用于验证以下五层结果，而非只验证最终文本：

1. Agent 意图与参数提取结果。
2. 多轮业务上下文及状态迁移。
3. `search_products` 的完整调用参数。
4. 商品筛选、排序和截取结果。
5. 最终用户回复与工具事实的一致性。

## 3. 业务范围

### 3.1 V1.0 范围内

- 商品品类：羽毛球拍。
- 意图：商品推荐 `product_recommendation`。
- 单轮与多轮自然语言交互。
- 推荐数量、价格、重量、品牌、颜色约束。
- 约束新增、覆盖、清除、冲突澄清和重新查询。
- 调用 `search_products` 查询在售且有库存的商品。
- 根据有效硬约束过滤商品并生成推荐结果。
- 查询无结果、工具失败和用户取消处理。
- 结构化 Trace 和测试所需的中间态观测。

### 3.2 V1.0 范围外

- 其他商品品类。
- 购物车、收藏、下单、支付、退款和物流。
- 用户画像、会员价、优惠券和个性化排序。
- 跨店比价、替代品推荐和搭配推荐。
- 语音、图片或视频输入。
- 真实生产流量、真实用户数据和真实商品交易。

范围外请求不得伪装成已支持能力。系统应说明当前仅支持羽毛球拍推荐。

## 4. 角色与外部系统

| 角色或系统 | 职责 |
| --- | --- |
| 用户 | 使用自然语言提出、修改、清除或取消推荐要求 |
| 智能导购 Agent | 识别意图、维护上下文、校验约束、调用工具并生成回复 |
| `search_products` | 按结构化条件返回商品数据或工具错误 |
| TestMesh | 保存需求、设计测试、构建 Dataset、运行 Experiment 并汇总证据 |
| Product Owner | 决定业务语义、批准需求版本和处理规则变更 |

## 5. 术语与数据定义

| 术语 | 定义 |
| --- | --- |
| 硬约束 | 推荐商品必须满足的条件，包括价格、重量、品牌、颜色、在售和库存条件 |
| 软偏好 | 仅影响满足硬约束商品的排序，不得突破硬约束 |
| 有效上下文 | 当前会话中已确认、未被覆盖或清除的业务参数集合 |
| 当前有效销售价 | 商品当前可成交价格，不是划线价、历史价或建议零售价 |
| 标准化 | 将别名、单位或自然语言表达转换成工具契约中的确定值 |
| 受控重试 | 仅对明确可重试的技术异常，使用相同业务参数最多重试一次 |
| 模拟业务 | 仅用于 TestMesh 工程验证，不代表真实公司系统和真实发布结论 |

### 5.1 标准参数模型

| 字段 | 类型 | 必填 | 业务含义 |
| --- | --- | --- | --- |
| `intent` | string | 是 | 固定为 `product_recommendation` |
| `category` | string | 是 | V1.0 固定为 `badminton_racket`，但必须由用户表达中明确识别，不得在品类不明时擅自补全 |
| `quantity` | integer | 是 | 推荐数量，默认值为 3 |
| `min_price` | decimal | 否 | 最低当前有效销售价，单位 CNY，包含边界 |
| `max_price` | decimal | 否 | 最高当前有效销售价，单位 CNY，包含边界 |
| `weight_min` | decimal | 否 | 最低标准化重量，单位 g，包含边界 |
| `weight_max` | decimal | 否 | 最高标准化重量，单位 g，包含边界 |
| `brand` | enum | 否 | 标准品牌编码 |
| `color` | string | 否 | 用户明确指定的颜色硬约束 |
| `sort_by` | enum | 是 | 默认 `recommendation_score`；轻量化语义下为 `weight` |
| `sort_order` | enum | 是 | `asc` 或 `desc` |

### 5.2 颜色语义

- 颜色是可选硬约束。
- V1.0 不维护颜色别名词典；去除首尾空白后，按商品目录中的规范颜色值进行精确匹配。
- 系统不得自行把“酒红”“粉红”等未登记表达映射为“红色”。
- 无法确定规范颜色值时进入 `NEED_CLARIFICATION`。

## 6. 核心业务规则

### BR-001：推荐数量

| 场景 | 规则 |
| --- | --- |
| 未指定数量 | 默认推荐 3 款 |
| 指定数量 | 允许 1～5 款，包含边界 |
| 数量为 0 或负数 | 参数无效，进入 `NEED_CLARIFICATION` 并要求重新输入 |
| 数量超过 5 | 不自动截断，提示最多推荐 5 款 |
| 满足条件的商品少于请求数量 | 返回实际数量并解释原因，不得放宽硬约束或虚构商品 |
| 满足条件的商品为 0 | 进入 `NO_RESULT`，告知无匹配商品并允许用户调整条件 |

### BR-002：价格与预算

| 场景 | 规则 |
| --- | --- |
| 未指定预算 | 不设置默认价格下限或上限 |
| 系统允许的最低输入价格 | 0 元/件 |
| 系统允许的最高输入价格 | 10,000 元/件 |
| 价格精度 | 标准化为两位小数，币种仅支持 CNY |
| “300 元以内” | `max_price = 300.00`，包含 300 元 |
| “300～500 元” | `min_price = 300.00`、`max_price = 500.00`，包含两端 |
| 输入价格小于 0 或高于 10,000 | 参数无效，提示系统支持范围 |
| 最低价格大于最高价格 | 约束冲突，进入 `NEED_CLARIFICATION` |

价格过滤必须使用商品当前有效销售价。10,000 元是输入上限，不是默认预算。用户未提出预算时，不得擅自传递 `max_price`。

### BR-003：重量与单位换算

统一使用克（g）作为标准重量单位。

| 用户输入单位 | 换算规则 |
| --- | --- |
| 克 / g | 直接使用 |
| 千克 / kg | `1 kg = 1000 g` |
| 斤 | `1 斤 = 500 g` |
| 两 | `1 两 = 50 g` |
| 盎司 / oz | `1 oz = 28.349523125 g` |

标准化结果保留两位小数，采用十进制四舍五入。所有比较基于标准化后的值。

| 自然语言 | 标准化规则 |
| --- | --- |
| “要轻一点的” | `weight_max = 85.00`，并按重量升序 |
| “80 到 85 克” | 闭区间 `[80.00, 85.00]` |
| “85 克以内” | `weight_max = 85.00`，包含 85g |
| “0.085 千克以内” | `weight_max = 85.00` |
| “再轻一点”且已有明确重量上限 | 不推测新值，进入 `NEED_CLARIFICATION` 询问新的重量目标 |

V1.0 未定义其他重量合法范围。遇到不支持的单位、非数值重量或无法确定的表达时必须澄清，不得由测试或模型自行制定阈值。

### BR-004：品牌别名

| 标准品牌编码 | 官方中文名 | 可识别别名 |
| --- | --- | --- |
| `YONEX` | 尤尼克斯 | Yonex、YY |
| `VICTOR` | 威克多 | Victor、胜利 |
| `LI_NING` | 李宁 | Li-Ning、Lining |
| `KAWASAKI` | 川崎 | Kawasaki |

处理规则：

1. 英文名称和别名匹配不区分大小写。
2. 工具调用统一传递标准品牌编码。
3. 未知品牌不得映射为已知品牌；应要求用户确认或告知暂不支持。
4. 单次查询最多指定一个品牌。
5. 同一轮出现多个备选品牌时，进入 `NEED_CLARIFICATION`。
6. 品牌词典是受控配置；新增或修改别名必须形成新配置版本并保留变更记录。

### BR-005：约束冲突与上下文更新

#### 不同轮次修改同一字段

采用“最新明确要求覆盖旧值”。未被提及的其他有效字段继续保留。

示例：

- 第一轮：`quantity=3, max_price=300`
- 第二轮：“预算改成 500 元”
- 更新后：`quantity=3, max_price=500`

#### 同一轮出现冲突的硬约束

系统必须：

1. 识别冲突。
2. 进入 `NEED_CLARIFICATION`。
3. 不调用 `search_products`。
4. 询问用户保留哪个条件。
5. 澄清完成后再重新校验和查询。

#### 不同字段的有效约束

价格、重量、颜色和品牌等条件组成交集。系统不得为了凑足推荐数量而放宽任一硬约束。

#### 软偏好与硬约束冲突

硬约束优先。示例：“必须 85～90g，希望越轻越好”表示保留 `[85,90]`，并在区间内按重量升序，不得推荐低于 85g 的商品。

### BR-006：上下文控制语句

| 用户表达 | 产品决策 |
| --- | --- |
| 未提及已有参数 | 保留有效上下文 |
| 明确修改某参数 | 新值覆盖旧值 |
| 新增参数 | 与现有约束合并 |
| “预算不限” | 清除 `min_price` 和 `max_price` |
| “不考虑品牌了” | 清除 `brand` |
| “重新推荐” | 保留条件并重新查询 |
| “重新开始” | 清空推荐上下文，回到 `IDLE` |
| 冲突未澄清 | 保留上一份有效上下文，不执行查询 |
| 查询无匹配商品 | 保留条件，等待用户调整 |
| 工具调用失败 | 不虚构商品；按 BR-008 处理 |
| “算了”等作用范围不明 | 询问是取消当前条件还是结束推荐 |
| 用户明确结束推荐 | 进入 `CANCELLED` |

### BR-007：筛选、排序与结果真实性

1. 查询条件固定包含 `status = ON_SALE` 和 `in_stock = true`。
2. 默认按 `recommendation_score desc` 排序。
3. “要轻一点的”以及在硬约束范围内“越轻越好”按 `weight asc` 排序。
4. Agent 必须对工具返回结果进行二次硬约束校验。
5. 工具返回的不合规商品必须被剔除并记录在 Trace 中。
6. 结果数量超过请求数量时，只返回排序后的前 N 款。
7. 商品不足时返回实际数量，不得补造、替换或放宽条件。
8. 商品名称、价格、重量、库存、品牌和颜色必须来自工具结果。

### BR-008：工具失败与受控重试

1. 超时、临时不可用或明确标识为可重试的技术异常，允许使用相同业务参数重试一次。
2. 参数错误、鉴权错误和业务拒绝不得重试，应进入 `FAILED`。
3. 一次重试后仍失败，进入 `FAILED` 并给出不包含内部敏感信息的错误提示。
4. 工具失败不得伪装成无结果或查询成功。
5. 重试次数、错误类别和最终状态必须进入 Trace。

## 7. 功能需求

| ID | 功能需求 | 验收要点 |
| --- | --- | --- |
| FR-001 | 系统应识别 `product_recommendation` 意图 | 非推荐意图不得调用商品查询工具 |
| FR-002 | 系统应从自然语言中提取并标准化有效参数 | 参数值符合第 5、6 章定义 |
| FR-003 | 系统应校验数量、价格、重量、品牌及字段间冲突 | 非法或不确定输入先澄清 |
| FR-004 | 系统应维护多轮有效上下文 | 未修改字段不丢失，修改字段正确覆盖 |
| FR-005 | 系统应支持按规则清除字段或重置会话 | 清除和重置范围符合 BR-006 |
| FR-006 | 只有校验通过后才能调用 `search_products` | `NEED_CLARIFICATION` 时工具调用数为 0 |
| FR-007 | 系统应传递完整工具参数 | 不允许只传 category、limit 的简写契约 |
| FR-008 | 系统应复核工具结果中的全部硬约束 | 硬约束满足率为 100% |
| FR-009 | 系统应按业务排序并截取结果 | 顺序和数量符合 BR-001、BR-007 |
| FR-010 | 系统应基于真实工具数据生成回复 | 不得虚构商品或属性 |
| FR-011 | 系统应处理无结果、失败和取消 | 状态与回复语义一致 |
| FR-012 | 系统应输出测试所需结构化 Trace | 满足第 10 章可观测性要求 |

## 8. 业务状态与状态迁移

### 8.1 状态定义

| 状态 | 定义 |
| --- | --- |
| `IDLE` | 尚无有效推荐上下文，等待用户输入 |
| `VALIDATING` | 正在提取、标准化并校验当前输入与上下文 |
| `NEED_CLARIFICATION` | 缺少必要参数、参数不合法、表达不确定或约束冲突 |
| `READY` | 参数和上下文校验通过，允许查询 |
| `SEARCHING` | 正在调用 `search_products` 或执行一次受控重试 |
| `NO_RESULT` | 工具调用成功，但没有满足全部硬约束的商品 |
| `SUCCEEDED` | 已返回符合条件的推荐结果，保留上下文等待下一轮 |
| `FAILED` | 工具异常且无法恢复，未产生伪造推荐 |
| `CANCELLED` | 用户明确终止当前推荐 |

### 8.2 状态迁移规则

| 当前状态 | 触发条件 | 下一状态 | 是否允许调用工具 |
| --- | --- | --- | --- |
| `IDLE` / `SUCCEEDED` / `NO_RESULT` | 收到新输入 | `VALIDATING` | 否 |
| `VALIDATING` | 校验不通过或需要澄清 | `NEED_CLARIFICATION` | 否 |
| `VALIDATING` | 校验通过 | `READY` | 否 |
| `READY` | 发起查询 | `SEARCHING` | 是 |
| `SEARCHING` | 有合规商品 | `SUCCEEDED` | 已完成 |
| `SEARCHING` | 无合规商品 | `NO_RESULT` | 已完成 |
| `SEARCHING` | 不可恢复错误 | `FAILED` | 已完成 |
| `NEED_CLARIFICATION` | 用户完成澄清 | `VALIDATING` | 否 |
| 任意非终止状态 | 用户明确结束 | `CANCELLED` | 否 |
| 任意状态 | 用户“重新开始” | `IDLE` | 否 |

只有 `READY` 可以进入 `SEARCHING`。上一份有效上下文必须与尚未确认的候选更新分开保存，冲突未澄清时不得污染有效上下文。

## 9. `search_products` 工具契约

### 9.1 请求结构

```json
{
  "category": "badminton_racket",
  "limit": 3,
  "filters": {
    "min_price": 300.00,
    "max_price": 500.00,
    "weight_min": 80.00,
    "weight_max": 85.00,
    "brand": "YONEX",
    "color": "红色",
    "status": "ON_SALE",
    "in_stock": true
  },
  "sort": {
    "field": "recommendation_score",
    "order": "desc"
  }
}
```

规则：

- 无值的可选字段不得传空字符串、`null` 或模型猜测值，应从 `filters` 中省略。
- `limit` 使用最终有效的 `quantity`。
- 数值字段使用标准化后的十进制数值。
- `brand` 使用标准品牌编码。
- 默认查询必须包含在售和有库存条件。

### 9.2 响应所需最小字段

```json
{
  "code": 0,
  "data": {
    "total": 1,
    "products": [
      {
        "product_id": "P001",
        "name": "羽毛球拍 A",
        "current_price": 299.00,
        "currency": "CNY",
        "weight_g": 83.50,
        "brand": "YONEX",
        "color": "红色",
        "stock": 8,
        "status": "ON_SALE",
        "recommendation_score": 0.91
      }
    ]
  }
}
```

以下字段缺失时，不得生成依赖该字段的事实性描述：`product_id`、`name`、`current_price`、`currency`、`weight_g`、`brand`、`color`、`stock`、`status`。

## 10. 可观测性与证据要求

每轮交互应通过结构化 Trace 或受控调试接口提供：

| 字段 | 要求 |
| --- | --- |
| `trace_id` | 每轮唯一关联标识 |
| `conversation_id` | 会话关联标识 |
| `turn_id` | 当前轮次标识 |
| `intent` | 识别后的业务意图 |
| `raw_slots` | 当前轮原始提取值 |
| `normalized_slots` | 当前轮标准化值 |
| `previous_context` | 本轮处理前的有效上下文 |
| `candidate_context` | 合并当前输入后的候选上下文 |
| `effective_context` | 校验通过后生效的上下文 |
| `state_before` / `state_after` | 业务状态迁移 |
| `validation_errors` | 非法、缺失、歧义或冲突详情 |
| `tool_calls` | 工具名、完整参数、开始时间、结果码、错误分类和重试次数 |
| `filtered_product_ids` | 被硬约束复核剔除的商品及原因 |
| `recommended_product_ids` | 最终推荐商品 ID，顺序必须与回复一致 |
| `final_response` | 最终用户回复 |

不得记录模型内部思维过程。测试不得只根据最终回复反推内部参数或工具调用正确性。

## 11. 用户回复要求

### 11.1 成功推荐

回复至少应包含：

- 实际返回数量。
- 商品名称和商品 ID。
- 与用户条件直接相关的价格、重量、品牌或颜色事实。
- 商品不足时的明确说明。

### 11.2 需要澄清

回复应指出需要确认的字段或冲突条件，并提出一个可回答的问题。不得在同一轮调用商品查询工具。

### 11.3 无匹配结果

回复应说明没有同时满足当前全部条件的商品，并允许用户修改条件。不得擅自放宽条件。

### 11.4 工具失败

回复应说明当前无法完成查询，可建议稍后重试；不得声称“没有商品”，不得虚构推荐结果，也不得暴露内部堆栈、密钥或敏感配置。

## 12. 产品验收标准

以下标准为 V1.0 强制准入条件：

1. 默认值、价格边界、重量换算和品牌映射符合本文档。
2. 有效硬约束满足率为 100%。
3. 不得虚构商品、价格、重量、库存、品牌、颜色或工具状态。
4. 已确认的多轮约束不得无故丢失。
5. 无法确定参数或存在冲突时必须先澄清。
6. 商品不足时允许少于请求数量，不得凑数。
7. 工具失败不得伪装成查询成功或无结果。
8. `NEED_CLARIFICATION` 状态下 `search_products` 调用次数必须为 0。
9. 工具参数、筛选结果、推荐 ID 和最终回复必须可通过 Trace 关联。
10. 评测结果必须标记为 `simulated`，不得作为真实生产发布证据。

上述要求属于业务正确性门禁，不直接等同于大模型整体准确率。

## 13. 测试设计与评测映射

### 13.1 测试条件最小集合

- 默认数量及数量边界：未指定、1、5、0、负数、6、库存不足、无结果。
- 价格边界：0、300、10,000、负数、超过 10,000、区间边界、反向区间、预算不限。
- 重量换算：g、kg、斤、两、oz、四舍五入、闭区间、未知单位、“再轻一点”。
- 品牌：标准名、中文名、别名、大小写、未知品牌、多品牌冲突、清除品牌。
- 多轮上下文：保留、新增、覆盖、清除、重新推荐、重新开始、冲突未澄清。
- 排序：默认排序、轻量化升序、硬约束与软偏好并存。
- 结果处理：超量截取、数量不足、0 结果、工具返回违规商品、字段缺失。
- 工具异常：可重试异常、不可重试异常、重试后失败。
- 状态：所有合法迁移及禁止迁移。

### 13.2 Dataset 规则

- Dataset 样本必须来源于已批准 TestCase。
- 每个样本应保存输入对话、初始上下文、预期标准化参数、预期状态、预期工具调用和预期推荐 ID。
- 边界、冲突、无结果和失败样本必须单独建组，不得只使用成功样本。
- Dataset 版本冻结后不得原地覆盖；规则变化必须生成新版本。

### 13.3 Experiment 规则

- Experiment 必须绑定明确的 Agent 版本、Prompt 版本、工具契约版本、品牌词典版本、Dataset 版本和 Evaluator 版本。
- Experiment 结果必须保留逐样本证据，不得只保留汇总分数。
- 固定工具夹具只能验证模拟工程链路，不代表真实商品系统质量。

### 13.4 Evaluator 职责边界

| Evaluator | 评价内容 |
| --- | --- |
| 参数提取 Evaluator | 标准化参数与预期是否完全一致 |
| 上下文 Evaluator | 有效上下文的保留、覆盖和清除是否正确 |
| 状态 Evaluator | 状态及迁移是否符合第 8 章 |
| 工具调用 Evaluator | 工具名、完整参数、调用次数和重试是否正确 |
| 硬约束 Evaluator | 每个推荐商品是否满足全部有效硬约束 |
| 真实性 Evaluator | 回复事实是否全部来自工具结果 |
| 回复质量 Evaluator | 是否完成必要说明、澄清或错误提示 |

确定性规则优先使用程序化断言。LLM-as-a-Judge 只用于无法通过结构化字段确定的表达质量，不得重新定义业务真值。

## 14. 非功能与安全约束

- V1.0 不设正式响应时间、吞吐量和并发 SLA；测试不得自行假定性能目标。
- 所有价格计算采用十进制，不使用二进制浮点近似作为业务比较结果。
- 工具错误回复不得暴露密钥、认证信息、内部地址或堆栈。
- 模拟商品、会话和 Trace 不得包含真实个人数据。
- 品牌词典和业务规则变更必须版本化并可追溯。

## 15. 假设、依赖与风险

### 15.1 依赖

- `search_products` 能够接受第 9 章请求结构。
- 商品数据提供当前有效销售价、标准重量、库存、状态、品牌和颜色。
- 测试环境能够提供第 10 章的结构化证据。

### 15.2 风险

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 工具字段与 PRD 契约不一致 | 无法进行确定性断言 | 开发前完成接口契约评审 |
| 商品数据缺字段 | 回复事实不可验证 | 缺失字段不得用于推荐描述，并记录证据缺口 |
| 模型自行补规则 | 产生不可重复结果 | 以本文档和版本化配置作为唯一业务真值 |
| LLM Judge 替代业务断言 | 业务错误被主观评分掩盖 | 硬约束使用程序化 Evaluator |

## 16. 需求变更与版本管理

1. 本文档冻结后不得原地覆盖。
2. 修改业务规则必须形成新的 PRD 修订版并重新评审。
3. 新版本必须关联前一基线、变更原因、受影响规则和测试资产。
4. 品牌词典、工具契约、Dataset 和 Evaluator 均需独立版本化。
5. 规则变更后，应评估 TestCondition、TestCase、Dataset 和 Evaluator 是否需要重建或回归。

## 17. 批准结论

Product Owner 确认：

- 本文档作为模拟智能导购业务 V1.0 的正式需求基线。
- 后续 TestMesh 工作应先进行结构化业务建模，再进行风险分析、测试条件、TestCase、Dataset、Experiment 和 Evaluator 设计。
- 业务语义以本文档为准，不由测试人员、实现代码或 Evaluator 自行决定。
- 当前批准的是需求与验收标准，不代表研发实现、自动化测试或发布准入已经完成。
