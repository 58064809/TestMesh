# 专业测试分析与规划

先阅读完整 PRD，再以批准基线限定可采信结论。不得直接从需求 ID 列表生成步骤。

## 工作顺序

1. 建立业务视图：模块、角色、入口、端到端流程、替代流程、规则、状态、数据对象、外部系统和可观察结果。
2. 按业务失败后果识别风险，不把技术名词本身当作风险。
3. 将每个基线项拆成一个或多个可独立判断成败的测试条件；正常、异常、边界、规则组合、状态迁移和跨系统交互是不同测试条件。
4. 为每个测试条件选择最合适的技法并说明覆盖项。不要用“场景分析”掩盖本应使用的边界值、判定表或状态迁移。
5. 先完成测试点与覆盖规划，再生成原子 TestCase。每条 TestCase 只有一个主要验证对象和一个场景/场景大纲。
6. 用来源证据核对测试数据和预期结果；未定义的阈值、状态或动作只能标记待配置/待澄清，不能猜测。

## 完成标准

- 每个未排除基线项至少作为一条原子 TestCase 的主要验证对象。
- 复杂条目按独立分支展开，不能因为已被某条用例顺带引用就视为充分覆盖。
- 测试步骤与预期结果一一对应，结果必须业务可观察。
- 追溯到真实 source ID，且关联来源足以支持测试数据和预期结果。

具体覆盖定义见 [ISTQB 测试设计参考](references/istqb-techniques.md)。
